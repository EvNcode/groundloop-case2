# GroundLoop

Рабочий сайт: https://evncode.github.io/groundloop-case2/

GroundLoop ведёт контейнер с кофейным жмыхом от кофейни до производственной партии и продажи. Сотрудник входит по личной рабочей почте и паролю; вход по почтовой ссылке также доступен. Администратор приглашает сотрудника, назначает роль и, для бариста, точку. Сотрудник подтверждает почту и задаёт пароль. Самостоятельная регистрация в Supabase Auth закрыта. В интерфейсе нет переключения ролей.

## Рабочий процесс

1. **Бариста** взвешивает контейнер, отмечает число напитков, сам проверяет качество и записывает замечания. Чистый контейнер появляется в очереди логиста. Сомнительный остаётся на точке. До вывоза автор может исправить или отменить запись; отмена сохраняется в журнале.
2. **Логист** начинает собственный рейс, видит филиал, бариста и адрес вывоза, добавляет готовые контейнеры и сканирует QR-код при получении. Другой логист не видит и не изменяет его рейс. Вывоз можно отменить до приёмки в цехе. При разрешении телефона GPS координаты рейса обновляются в базе; руководство видит положение и время последнего сигнала.
3. **Производство** сканирует тот же код при приёмке. Оператор может отменить ошибочную приёмку до формирования партии. Из принятых контейнеров создаётся партия, фиксируются вес после сушки, пригодный вес и фактический выпуск.
4. **Управление** видит операции и GPS рейсов, записывает продажи готовых упаковок. Администратор приглашает сотрудников, меняет роли и точки, отключает доступ и ведёт адреса филиалов. Обычный руководитель не может менять доступ. Сервер не позволяет продать больше выпущенного.

События передаются через Supabase Realtime с резервным обновлением каждые 20 секунд. Все переходы, принадлежность записи сотруднику, сканы и остаток проверяются триггерами и RLS в Postgres. Управление не утверждает записи бариста: оценку качества делает бариста на точке.

## Доступ и запуск

- В Supabase Auth Site URL и разрешённый адрес возврата настроены на `https://evncode.github.io/groundloop-case2/`. Email включён, подтверждение почты обязательно, анонимный вход и самостоятельная регистрация выключены. Почтовый вход использует `shouldCreateUser: false`.
- Первый администратор: `hairullanurlybakyt@gmail.com`. Только он управляет командой и отправляет приглашения через серверную Edge Function `groundloop-invite`. В ней повторно проверяется действующая Auth-сессия и право администратора. Для нового сотрудника ссылка из письма открывает экран установки пароля.
- Для показа созданы отдельные аккаунты двух бариста, двух логистов, одного оператора производства и двух руководителей. Их пароли не хранятся в репозитории. Обычные руководители видят операции и продажи, но не управляют доступом команды.
- Адрес вывоза хранится у точки и показывается логисту в заявке. Исторические тестовые точки пока имеют только названия и районы: администратор должен внести точные адреса перед реальным вывозом.
- Для сканирования нужен доступ браузера к камере. При недоступной камере можно ввести код с этикетки. GPS включается логистом на телефоне и требует разрешения геолокации; без него остальные функции работают.
- Работа с Coyote POS пока не подключена: данные о контейнере вводит бариста, а рабочую почту приглашает администратор GroundLoop. Для единого входа через Coyote потребуется его SSO/OIDC или иной официальный способ проверки сотрудников. Для автоматической загрузки понадобятся API или отчёт Coyote с точкой, временем, числом напитков и весом, если вес там измеряется. Для карты маршрута с расчётом времени понадобятся координаты точек и маршрутизатор. Текущий GPS использует встроенный Geolocation API браузера, карта — OpenStreetMap.

Локально:

```powershell
npm ci
npm run build
npm test
python -m http.server 8789 --directory dist
```

SQL миграции находятся в `supabase/migrations/`. `tests/workflow.sql` проверяет весь путь в транзакции с откатом. GitHub Actions собирает и публикует `dist/` на GitHub Pages после push в `main`. В клиенте находится только Supabase publishable key; серверных секретов нет.

## Границы результата

В операционной базе есть проверочные записи четырёх аккаунтов: четыре активных контейнера, один рейс, одна готовая партия и продажа. Они нужны для показа процесса и не являются фактическими замерами сети. Старые учебные записи хранятся отдельно и в показатели нового сайта не попадают. Физический образец подставок, замеры выхода материала и проверка себестоимости на реальных объёмах требуются для окончательной защиты кейса 2.
